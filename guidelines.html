02 — The evaluation

From friction to findings.

A first-pass WCAG 2.2 review of the Quora question-creation journey. Observations are separated from issues that still require HTML or assistive-technology verification.

Observed in testingNeeds verificationDesign recommendation

How to read this page

Evidence before conclusions

A screenshot can show a visual problem, but it cannot prove what a screen reader announces or what role an element exposes. Keyboard and VoiceOver observations are reported as user-test findings. HTML-related issues remain verification targets until the relevant DOM and accessibility tree have been inspected.

Scope note

This is a preliminary manual evaluation, not a formal conformance certification. A criterion is only described as a confirmed violation when the available evidence supports that conclusion.

01 — WCAG findings

Potential barriers across the flow

The criteria below are the most relevant to the observed journey. “Needs verification” means the issue is plausible but not yet proven from the available screenshots.

01Observed in testing

Keyboard navigation is difficult to follow

WCAG 2.1.1 — Keyboard (Level A) · 2.4.3 — Focus Order (Level A)

The user reported that the flow was not easy to use with only a keyboard. They tested reaching the Add Question control, opening the modal and interacting with the duplicate-question warning. The exact focus sequence and whether every control is operable still need a repeatable test.

Usability impact

Keyboard users may have difficulty reaching controls, understanding where focus has moved or completing the question flow without a pointer.

Design recommendation

Make every action keyboard-operable, provide a clear visible focus indicator, preserve a logical focus order and manage focus when dialogs open and close.

02Observed in testing

Screen-reader output is difficult to map to the interface

WCAG 1.3.1 — Info and Relationships (Level A) · 1.3.2 — Meaningful Sequence (Level A) · 4.1.2 — Name, Role, Value (Level A)

During VoiceOver use, the tester found it difficult to identify some announced elements visually and reported that content could be read in an illogical order. Because the tester was also unfamiliar with VoiceOver, this observation should be retested after learning the basic navigation commands.

Usability impact

Users may lose their place or be unable to connect an announcement with the control or content it describes.

Design recommendation

Use semantic landmarks, headings, lists and controls; give interactive elements descriptive names; and ensure the DOM order follows the meaningful reading sequence.

03Observed in testing

Dialog changes are not sufficiently clear to the screen-reader user

WCAG 4.1.2 — Name, Role, Value (Level A) · 2.4.3 — Focus Order (Level A)

The duplicate-question and question-creation dialogs were difficult to navigate with a keyboard and screen reader. The tester also reported difficulty recognising the modal transition. The dialog role, accessible name, focus placement and focus containment need DOM and keyboard verification.

Usability impact

A user may not realise that a new dialog has opened or may continue navigating content behind it.

Design recommendation

Use a correctly labelled native dialog or equivalent dialog pattern, move focus into it when opened, keep focus within it while modal, support Escape where appropriate, and return focus to the invoking control when closed.

04Observed in testing

Validation feedback was not clearly announced

WCAG 4.1.3 — Status Messages (Level AA) · 3.3.1 — Error Identification (Level A)

The tester reported that the validation error was not announced as expected. The screenshot shows an orange message asking the user to add more detail and write a complete sentence. The live-region implementation and association with the question field have not yet been inspected.

Usability impact

A screen-reader user may not know that an error appeared, why the action failed or which field needs attention.

Design recommendation

Announce dynamically inserted feedback without unexpectedly moving focus. Associate field-specific errors with the input and provide a clear correction instruction.

05Needs verification

The question field may rely on placeholder text

WCAG 3.3.2 — Labels or Instructions (Level A) · 4.1.2 — Name, Role, Value (Level A)

The visible prompt in the question field reads “Start your question with ‘What’, ‘How’, ‘Why’, etc.” This screenshot does not reveal whether a persistent programmatic label is present in the HTML.

Usability impact

If placeholder text is the only label, users may lose the prompt while typing or have difficulty identifying the field later.

Design recommendation

Provide a visible, persistent label such as “Your question” and use the placeholder only as an example or hint.

06Needs verification

Icon-only controls may lack accessible names

WCAG 4.1.2 — Name, Role, Value (Level A) · 2.4.6 — Headings and Labels (Level AA)

The interface contains icon-only controls, including close and navigation icons. The screenshots cannot establish whether each control has a computed accessible name.

Usability impact

A screen reader may announce a generic “button” without explaining its purpose.

Design recommendation

Give each icon button a concise accessible name, such as “Close Add Question dialog”, and hide purely decorative icon artwork from the accessibility tree.

07Needs verification

Image-based posts may hide information from non-visual users

WCAG 1.1.1 — Non-text Content (Level A)

The home feed includes a post where much of the message is embedded in an image. The screenshot demonstrates image-based content, but its actual alternative text must be inspected before confirming a failure.

Usability impact

If the image contains meaningful text and has no equivalent text alternative, a screen-reader user may miss the post's central message.

Design recommendation

Provide concise alt text that communicates the image's purpose, and include important text from image-based posts in the post's accessible text content.

08Needs verification

Dense layout, contrast and target sizes may create additional barriers

WCAG 1.4.3 — Contrast (Minimum) (Level AA) · 1.4.11 — Non-text Contrast (Level AA) · 2.5.8 — Target Size (Minimum) (Level AA)

The feed combines several navigation areas, image-led posts and advertisements. Small icons and muted text are visible in the screenshots, but contrast ratios and target dimensions have not been measured.

Usability impact

Low contrast can make text and controls harder to perceive. Small targets can be difficult to activate for people with limited dexterity.

Design recommendation

Measure text and component contrast, enlarge interactive hit areas where needed, and create clearer visual separation between primary content and advertising.

Screen-reader guidance

What a clear experience should communicate

These are expected outcomes to test, not a transcript of what Quora currently announces.

1. Entering the page

A screen-reader user should be able to identify the page title, navigate by headings and landmarks, and skip repeated navigation to reach the main content.

Listen for: page title · main landmark · heading structure · navigation landmark

2. Opening Add Question

When the dialog opens, focus should move into it and the dialog's purpose should be announced. The close control and tabs should have understandable names, roles and states.

Example announcement: “Add Question, dialog.”

3. Entering a question

The text-entry control should expose a persistent label. Instructions should be available without relying on placeholder text alone.

Example announcement: “Your question, text area.”

4. Receiving duplicate or validation feedback

New feedback should be announced without forcing the user to search for it. The similar question and next-step actions should be discoverable, and an error should be associated with the field it describes.

Example announcement: “A similar question was found.”

5. Closing or returning to the form

When a dialog closes, focus should return to a meaningful place, usually the control that opened it. The user's entered text should remain available when the flow allows correction.

Test with: keyboard only · VoiceOver · Chrome accessibility tree

Testing note for VoiceOver

VoiceOver has its own navigation model and keyboard commands. Before attributing every confusing announcement to the website, repeat the test after becoming comfortable with basic VoiceOver navigation. Record the exact phrase heard, the focused element and the action that caused the announcement.

02 — Code patterns

What inaccessible code can look like

These are illustrative examples for the assignment. They are not copied from Quora and should not be presented as Quora's actual HTML.

Problematic pattern

Input with no persistent label

<textarea
  placeholder="Start your question..."
></textarea>

A placeholder alone is not a reliable replacement for a persistent label.

Improved pattern

Explicitly labelled input

<label for="question">Your question</label>
<textarea
  id="question"
  name="question"
  placeholder="Start with What, How, or Why"
></textarea>

The visible label is programmatically associated with the text area.

Problematic pattern

Unlabelled icon button

<button>
  <svg>...</svg>
</button>

The button may have no meaningful accessible name if its icon is the only content.

Improved pattern

Named icon button

<button type="button"
  aria-label="Close Add Question dialog">
  <svg aria-hidden="true">...</svg>
</button>

The accessible name describes the action; the decorative icon is hidden from assistive technology.

Problematic pattern

Unannounced error container

<div class="error">
  This question needs more detail.
</div>

If this message is inserted dynamically, it may not be announced automatically.

Improved pattern

Associated, announced error

<label for="question">Your question</label>
<textarea id="question"
  aria-invalid="true"
  aria-describedby="question-error">
</textarea>
<p id="question-error">
  Add more detail to your question.
</p>
<div role="alert">
  Your question needs more detail.
</div>

The field is identified as invalid and references its explanation. Use an alert for a newly occurring, important error announcement; avoid duplicate announcements if the same message is already associated and announced.

Problematic pattern

Dialog without clear semantics

<div class="modal">
  <h2>Add Question</h2>
  ...
</div>

A generic container does not, by itself, expose dialog semantics or modal behaviour.

Improved pattern

Named dialog pattern

<dialog
  aria-labelledby="dialog-title">
  <h2 id="dialog-title">Add Question</h2>
  ...
</dialog>

A native dialog opened modally with showModal() provides dialog semantics and modal behaviour. Focus management and a sensible close path still need to be implemented and tested.

03 — Redesign direction

Design recommendations

01

Make structure explicit

Use landmarks, a logical heading hierarchy, labelled controls and meaningful text alternatives.

02

Keep focus predictable

Make keyboard focus visible, move it into newly opened dialogs and return it to the trigger when the dialog closes.

03

Explain errors in context

Announce dynamic feedback, identify the field in error and preserve the user's entered text wherever possible.

04

Reduce competing content

Give the primary task a clear visual hierarchy and avoid letting ads or secondary actions overwhelm the question flow.
